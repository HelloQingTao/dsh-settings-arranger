# settings-arranger「导航配置存为配置文件」可行性分析（已拍板：全局统一单文件）

> 结论先行：**可行，且是低风险改造**。现状是排布存在浏览器 localStorage（键 `dsh.settings-arranger.v1`），按浏览器+站点隔离——换浏览器、换端口、网页版与桌面版互不相通，浏览器清数据就丢。方案 = 给插件补上 host 半边（`index.js` 目前是空壳），注册一个仅回环可达的路由，把排布落成**一份全局统一的配置文件** `~/.dsh/settings-arranger.json`；localStorage 降级为同步缓存与降级兜底，旧数据首次自动迁移上载。host 路由 + webServer 机制已由 dsh-railist 在本机 web/desktop 两个 profile 实测跑通（`~/.dsh/railist.json` 同时存在 `web`、`desktop` 分节即为证据），不需要任何新的运行时能力。
>
> **2026-10-24 用户拍板**：存储形态选「全局统一单文件」而非「按 profile 分文件」——两个 profile 本质是同一个 DSH 的两个入口，排布偏好没有按 profile 差异化的真实需求；将来真要差异化，从统一文件复制拆分是无损的，反向合并才有损。

---

## 1. 现状与问题

- **现在是什么样**：
  - dsh-settings-arranger 是纯客户端插件（`index.js` 4 行空壳，全部逻辑在 `client.js` 1205 行），持久化收口在三个函数：`loadState()`（`client.js:30`）、`saveState()`（`client.js:53`）、`clearState()`（`client.js:57`），数据键 `dsh.settings-arranger.v1`，内容为 `{groups, collapsed, order, lastSection}`；变更路径为「改内存 → 同步写 localStorage → `apply()` 重排」。
  - 本机安装现状：web profile = 0.1.4，desktop profile = 0.1.3（两 profile 版本已脱节，本次发版需两边一起更）。
- **问题是什么**：排布跟着浏览器走而不是跟着用户走——
  1. 换浏览器 / 换端口（origin 变了）排布全丢，要重新整理一遍；
  2. 网页版（web profile）和桌面版（desktop profile）各存各的 localStorage，**网页版整理完桌面版还得重新整理一遍**；
  3. 浏览器清除站点数据 = 排布永久丢失，无兜底，也没有一个看得见、可备份的文件。
- **影响谁**：所有装了这个插件的用户（尤其同时在网页版和桌面版用的）。
- **为什么现在处理**：这是下一个要开发的功能，用户要求先拍板技术路线。

## 2. 这个方案解决什么

- **解决**：
  1. 排布持久化从 localStorage 升级为**磁盘配置文件**：`$DSH_HOME/settings-arranger.json`，全局统一一份（web 和 desktop 共享，一端整理两端生效），文件 0600、原子写入、内容人类可读可手改。
  2. localStorage 转为**同步镜像缓存**：启动瞬间先用它画排布（避免异步取数闪一下原生顺序），服务端数据到达后以文件为准纠正。
  3. **自动迁移**：首次读到「文件不存在且 localStorage 有排布」时，把 localStorage 内容 PUT 上载成文件，一次性完成，无需用户操作。
- **不解决**：不做按 profile 差异化排布（拍板结论：不需要）；不做云端同步；不改任何重排/分组/拖拽的 DOM 逻辑。
- **为什么不用别的办法**（2026-10-24 对比后用户拍板）：
  - **方案 B（保持 localStorage）**：问题原样保留，否决。
  - **方案 C（按 profile 分文件 `settings-arranger/<profileId>.json`）**：可行，但两个 profile 是同一个 DSH 的两个入口，排布偏好天然一致，分开存意味着两边各整理一遍——恰是本次要消灭的痛点；导航树因两 profile 插件集不同而不一致时，靠「排布里多余的 id 忽略、树里新增的 id 追加默认位」容错，这本就是必做的健壮性。将来真要差异化，从统一文件复制拆分无损。**作为备选保留**。
  - **方案 D（塞进 DSH 官方 settings 存储）**：排布是插件自有的高频变更状态，不是用户要调的设置项，按配置落位规则应放插件自己的文件。
  - **并发写疑虑的澄清**（曾作为倾向方案 C 的理由，已修正）：railist 的读-改-写竞态有害，是因为两个 profile 存**不同的**排序数据；本插件两端 PUT 的是**同一份**排布意图，防抖 300ms 下并发窗口极小，「最后写赢 = 最后一次整理生效」在排布语义下无害，原子 rename 保证文件不写烂。

## 3. 做完后用起来什么样

### 用户视角

- **入口/触发**：无新入口，使用方式完全不变——整理导航、拖拽、分组的每一步照旧。
- **成功反馈**：整理完的排布出现在 `~/.dsh/settings-arranger.json`；网页版整理，桌面版打开就是同一种排布；重启 dsh、换浏览器、换端口打开，排布原样回来。
- **失败反馈**：host 路由不可达（极端情况）时插件静默回退到「纯 localStorage」即今天的 v0.1.4 行为，控制台一条 `[dsh-settings-arranger]` warn，无报错循环、无 UI 打扰。

### 开发视角

- **host 半边**（`index.js` 重写，纯 JS 零新依赖，只用 `node:fs`）：
  - 通过 `ctx.inject(['webServer'], …)` 注册前缀路由 `/settings-arranger/api`（与 railist 的 `/railist/api` 同机制），端点：
    - `GET /config` → `{config | null, health}`；
    - `PUT /config`（body `{"layout":{…}}`）→ 同上；写前校验结构（version/字段类型/长度上限，宽松归一化，不引 ajv）；
    - `POST /reset` → 删除文件恢复「无排布」态。
  - **回环栅栏**：peer 地址必须是 127.0.0.1/::1 且 `Host` 头是回环域名（防 DNS rebinding），照搬 railist 已验证的 `isLoopbackRequest` 逻辑；body 上限 256 KB。
  - **不依赖 profileContext**：全局单文件，profile 解析整段不需要，host 半边反而更简单。
  - **写盘**：临时文件 0600 + rename 原子替换（Windows EPERM/EBUSY 回退直写）；读到的坏文件隔离为 `<file>.corrupt-<时间戳>` 后按「无排布」处理，绝不覆盖原文件。
  - **文件内容**：
    ```json
    {
      "version": 1,
      "updatedAt": "2026-10-24T19:30:00.000Z",
      "layout": { "groups": [], "collapsed": [], "order": null, "lastSection": null }
    }
    ```
    `layout` 就是现在 localStorage 的原样载荷，`version` 留给以后演进。
- **client 半边**（只动持久化层，DOM 逻辑零改动）：
  - `loadState/saveState/clearState` 语义不变（localStorage 镜像），在其外套一层「服务端同步」：挂载时先照旧渲染，随后 GET 文件——有内容则以文件为准重排；文件为空且 localStorage 有排布则 PUT 迁移。
  - `saveState` 追加一个 ~300ms 防抖的 PUT（拖拽连续变更合并成一次写盘）；PUT 失败仅 console.warn。
  - `snapshot()` 继续读 localStorage 镜像，读路径语义完全不变，改动面最小。

## 4. 出错怎么办

- **用户看到什么**：文件读写失败完全无感（localStorage 兜底，排布照常保存和恢复，只是「换浏览器不丢」暂时失效）；文件损坏时按默认排布启动。
- **系统怎么兜底**：读永不抛错——文件缺失/损坏/结构不合法一律按「无排布」降级并把原文件隔离留存；写失败保留 localStorage 副本，下次变更重试 PUT。
- **能不能重试**：PUT 按变更触发天然重试；损坏文件只在内容指纹变化时隔离一次，不会循环拷贝。
- **怎么回滚**：发版回滚到 0.1.4 即回到纯 localStorage 行为，配置文件留在磁盘上无害；新代码读旧数据（localStorage）、旧代码读新数据（不认识路由，继续 localStorage）双向兼容。
- **怎么排查**：控制台 `[dsh-settings-arranger]` 前缀日志；`GET /config` 的 `health` 字段带 configPath/writable/corruption 信息，直接 curl 可查。

## 5. 对现有功能影响 / 兼容

- **影响的老功能**：无 UI 变化、无交互变化；恢复默认从「只清 localStorage」变为「同时删配置文件」（行为更完整）。
- **兼容**：
  - 老 client + 新 host：旧版本根本不会调路由，无影响；新 host 只是被空占的 `index.js` 换成真实现，路由命名空间独立。
  - 新 client + 老 host（漏更某个 profile）：fetch 404 → 静默降级 localStorage，功能不坏。
  - **两 profile 都要发**（本机 web 已 0.1.4、desktop 还 0.1.3，正好借这次拉齐）；按规则本次顺带把 `engines.dsh` 补成范围声明 `">=0.2.0-rc.2 <0.3.0"`，`dsh.compatibility.dshReleases` 枚举按范围规则对齐。
- **并发**：同 profile 多开标签页、或两个 profile 同时整理，都是「最后写赢」——排布场景下即「最后一次整理生效」，可接受；原子 rename 保证文件不写烂。
- **主要风险（按可能性 × 后果排序）**：
  1. 桌面版 host 是否提供 `webServer` 服务（低 × 低）——**已用事证排除**：`~/.dsh/railist.json` 同时存在 web/desktop 分节，说明同一机制在桌面版已跑通；实施时仍按验收清单双 profile 实测。
  2. 迁移「先到先得」（低 × 低）：升级后第一个启动的入口把它那份 localStorage 上载成文件，其他入口/浏览器以文件为准收敛——这是「排布全局共享」的预期语义。
  3. 用户手改文件写坏（低 × 低）——隔离 + 降级 + 0600 权限已覆盖。

## 6. 实施顺序

1. **host 半边**：重写 `index.js`（store + 路由 + 回环栅栏 + 原子写 + 损坏隔离），配套测试（node:test 内置 runner，零 devDependencies；本包目前 0 测试，按工作区规则「重要功能节点必须交测试」补最小测试面：读写往返、结构归一化、损坏隔离、reset）。
2. **client 半边**：持久化适配层（启动 GET + 以文件为准 + 自动迁移 + 防抖 PUT + 失败降级），DOM/重排逻辑不动，补 1–2 个 client store spec。
3. **收尾**：`engines.dsh` 范围声明、版本 bump、README 中英双语补「配置文件位置与迁移说明」、build。
4. **双 profile 实测**：web 上验证迁移/落盘/重启保持/换端口保持；`dsh plugin --profile desktop add` 升级桌面版并验证 desktop 端共享同一文件生效。

依赖关系：2 依赖 1 的路由契约；3、4 顺序收尾。
